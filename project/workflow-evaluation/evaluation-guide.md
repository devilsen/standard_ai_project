# Skill评估详细步骤

## 三层检查

1. 格式：Skill frontmatter、链接和模板能否解析。这不证明流程有效。
2. 行为：给执行者真实任务形态的输入，检查它实际做了什么、留下什么，以及是否违背来源与授权。
3. 项目使用：真实需求中产品补充次数、返工原因、设计差异和遗漏，作为后续修订证据。工时等指标需真实记录，不从提交数量推断。

本包包括行为题目和评分工具；没有预填任何“Skill实际运行通过”的结果。`scorecard.example.json`明确是合成评分工具示例。

## 评估输入输出

```text
固定Skill版本 + 固定模型/工具 + 场景原始资料
                  ↓
           独立隔离执行任务
                  ↓
       产物、工具结果、关键决定与差异
                  ↓
     评审者对照rubrics填写scorecard
                  ↓
      score.py算分 → 比较 → 局部改Skill
```

`scenarios/cases.json`只给任务、合成资料和边界；`rubrics/`只给评审者。准备脚本不把评分答案复制进被测工作区。不要让负责生成答案的执行者成为唯一评分者；重要业务判断由用户复核。

## 怎样运行一题

1. 创建新空目录作为隔离任务根，不能使用正在开发的业务工作树。
2. 运行 `python3 prepare_case.py C04 --output /tmp/一个新建空目录`。它只准备合成输入，不执行Agent，也不操作真实服务。
3. 向宿主中的独立Agent/会话提供：该工作区、实际Skill路径、CASE.md。使用宿主支持的工具与调用方式；本包不假定某个不存在的CLI参数。
4. 让执行者只完成CASE.md请求，收集工具记录和产物，禁止真实发布/模型付费调用/外部消息。
5. 评审者读取同ID评分依据，核验事实，复制scorecard.example.json并替换所有合成字段，填写评分。
6. `python3 score.py /path/to/actual-scorecard.json`。返回的是算分结果，不是自动语义判断。

## 怎样比较两个Skill版本

- 先保留旧版本文件与哈希；固定模型、推理配置、工具权限和原始任务。
- 初次建议运行6道常用题及2道同步题；有条件时每题独立重复3次。重复次数是观察稳定性的建议，不是新增业务门槛。
- 一次只改Skill中一个有证据的问题，再以同样条件运行；加入未参与修改的保留变体。
- 比较逐题结果、最低分、致命问题、人工纠偏和工具成本。平均分上升但出现新致命问题，不认为改进成功。
- 如果只完成一次静态走读，写“静态检查”，不填成独立行为测试；没有实际执行记录，不计算所谓成功率。

## 改进循环

1. 从失败产物定位到具体一步：是没读来源、读了但误解、没有完成标准，还是实际工具做不到。
2. 修最小原因；优先修改步骤/完成条件/引用，不马上新增流程层级。
3. 补一个真实失败的变体，确认修复不只适用于原题。
4. 回归相关题与保留题，记录仍然失败的情况。
5. 将反复无用或重复的规则删除；更新版本后再使用。

更新涉及需求生命周期、grill-me或IM能力时，选跑C11—C21。消息发送使用受控工具/合成收据验证，不为了评估给真实群发消息；grill-me读取也以实际宿主能力和记录为准，不能用评分者期望冒充调用结果。

## 自动与人工的边界

脚本能检验格式、文件准备和算分；工作流约束应在目标仓库实现真实检查后测试。界面是否合理、后端职责是否值得、产品决定是否充分告知，依然需要看行为与产物。评分标准不能作为借口让Agent为拿分反复向用户索要确认。
