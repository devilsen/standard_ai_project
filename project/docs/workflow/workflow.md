# 工作流：每一步做什么

## 使用方式

本流程用于本项目已经选定的“独立设计 → 固定交接 → 正式实现 → 测试环境修复验证 → 飞书请用户验收 → 用户确认 → 发布staging → 更新设计底稿 → 最终通知”。用户明确要求本轮测试验收后才可发布staging，这是每次需求的交付边界；同一已确认版本不重复询问。常规实现选择与既有测试环境授权持续有效。

详细信息分别保存在设计/PRD、接口契约、case 和测试中；任务记录只引用它们和记录进度，不复制全部内容。小修复复用已有材料，说明哪些阶段已经满足即可。

## 推荐顺序

```text
0 定位现有设计/代码/规则，拿到案例与目标
1 在 designend 还原完整交互，产品交接
2 固定 API 契约、测试预期与后端职责
3 拆成按行为交付的小切片
4 每个切片完成测试、前后端实现和集成
5 在测试环境完成真实case、回归与修复；涉及界面时执行verify-ui对照与复验
6 飞书通知用户测试验收，等待该版本的明确确认
7 发布已确认版本到staging，完成上线后验证
8 从实际staging版本更新下一轮designend底稿并验证
9 最后分别通知用户和默认项目群，核验各自回执
```

“先前端还是先 API”：先通过 designend 看清需求，但这时不连接真实后端；接口设计可提前核实可行性，不能等完整设计完成才发现能力不成立。设计明确后先固定本轮契约，再让正式前后端按切片实现。已有稳定契约直接复用。不要先把所有正式前端、所有后端分别做完，再第一次联调。

## 阶段明细

| 步骤 | 输入 | 做什么 | 留下什么 | 完成条件 |
|---|---|---|---|---|
| 0 接需求 | 用户目标、仓库、已有资料 | 读现有材料、确认来源、识别本轮范围；收集缺少的case输入，按PRD制定独立预期 | task.md 引用、case.md | 目标/输入/输出有依据；未知和可继续工作可区分 |
| 1 做设计 | 上线底稿、PRD、案例 | 先演示正常流程，再演示本轮关键异常；补齐每个操作后的状态与跳转 | 独立 designend、mock 场景、PRD、交接记录 | 研发可以实际操作；界面与PRD一致；交接提交明确；重要歧义已解决 |
| 2 定契约 | 已交接设计、现有 API/后端 | 复用现有能力，定义真正新增接口；设计内部职责与失败边界 | OpenAPI、apiend 展示、task 中的边界说明 | 前后端/mock对字段与错误含义一致；相关历史兼容有处理 |
| 3 拆工作 | 设计/契约/case | 建立行为到测试映射；按可观察价值拆切片与依赖 | test-plan.md、slice.md 列表 | 每片有独立演示、测试、范围和完成标准；依赖是真实阻塞 |
| 4 做实现 | 一片就绪任务 | 测试一个行为、看到有效失败、最小实现、聚焦回归；前后端真实衔接；代码检查 | 实现、测试、切片结果 | 行为通过，未擅改产品规则，受影响检查通过或明确缺口 |
| 5 测试环境验证修复 | 固定实现、设计、真实case、测试环境 | 验证行为；涉及UI时执行verify-ui同场景对照、修复与复验 | 测试版本、功能结果、UI成对截图/差异记录及剩余项 | 功能与UI分别有结论；缺图/未测/失败不冒充通过，不把staging当开发测试机 |
| 6 用户测试验收 | 测试环境通过的版本与入口 | 飞书私聊用户，请按case验收；记录答复，问题返回步骤4/5 | 与版本绑定的明确确认 | 用户本人或明确授权决定人确认本轮测试结果；沉默/测试绿/群意见不算确认 |
| 7 发布staging | 已确认版本、发布范围、现有发布规则 | 核对确认仍适用，发布同一版本并验证真实业务 | staging运行版本、发布与验证结果 | 测试确认与实际发布一致；失败时如实报告、按已有恢复方案处理 |
| 8 回写底稿 | 实际staging版本、设计工作区 | 保护未交付设计，更新底稿、保留mock并验证 | 同步提交、来源、差异与交付记录 | 无设计丢失，mock可用，底稿与实际发布界面对应 |
| 9 最终IM交付 | staging验证、底稿同步与交付记录 | 分别给用户和默认群发结果、入口、版本及限制，核验回执 | 私聊和群各自message_id/状态 | 最后一步；两路分别记录，失败只续办未完成通知，不重发已成功消息 |

## 阶段 0：先理解，而不是先写代码

1. 阅读根规则、相关目录规则、当前页面、PRD、接口与已有测试；仓库中能确定的信息不要再问用户。
2. 写出本次目标、用户动作和预期输出，注明依据。新产品行为与技术假设分别标识。
3. 开始时主动检查已有case，向用户索取缺少的真实输入、业务目标与授权；Agent按已批准PRD、原文及领域规则在执行前制定独立预期、允许差异和失败条件。无需用户逐项设计研发测试；无法由来源确定的产品选择再澄清，最终case和结果交用户复核。
4. 缺 case 不必阻止界面和接口的独立工作，但不能编造真实验收。语义不明确会影响接口或实现的部分先问；每次聚焦一个关键决定。

## 阶段 1：可操作设计是交接物

先确认设计基于哪个上线版本，然后围绕 case 操作界面。PRD 描述难以单靠页面表达的条件、权限、数据含义和异常；不再写一份重复页面清单。

交接前列出本轮变化：新增操作、状态、入口、输出，以及全局组件/样式影响。产品可先交付一个边界明确的小范围，研发按该范围推进。设计“有待确认”不能自动当成通过。

## 阶段 2：API 与后端边界

先读已有调用方与实现。按实际需求检查：权限/归属、数据含义、异步状态、文件引用、幂等、取消、分页、部分失败、兼容、外部依赖。只填写涉及的项。

后端至少解释：谁持有业务状态；谁写数据；在哪里开始/结束事务；哪里调用外部服务；失败后谁恢复。不为了填目录新增仓储/工厂/总线。真实输入规模造成的问题需要明确处理，不能自行加产品配额。

## 阶段 3：按行为切片

先列测试场景，再逐条写具体测试和实现。一个切片回答“用户能多完成什么，或哪条独立能力被验证”。阶段1的设计交接和阶段2的契约是共享前置成果，不拆成数十个无法独立验收的开发票。

示例：展示已有结果 → 提交并保存一次装配 → 展示真实进度/失败 → 从结果调整。实际切片随需求选择，不是每个项目都要这些功能。

- 一片太大：把不同用户动作或失败恢复拆开，但每片保留所需前后端与测试。
- 一片太碎：只有“写一个schema/按钮/SQL”却无法独立验证能力时合并回所属行为。
- 依赖：缺接口契约是真阻塞；“团队习惯先写后端”不是依赖。
- 切片中新增业务决定、数据迁移或公共组件影响时更新范围与测试，不能悄悄扩大。

## 阶段 4：测试与实现节奏

1. 选择一个已定义的可观察行为；预期来自已确认的 case/设计/契约。
2. 在最近的公共边界写测试，运行并确认因缺失行为失败，而不是环境或语法错误。
3. 写最小实现，运行同一测试和受影响检查。
4. 检查职责、重复、依赖和全局影响；需要重构时在行为测试为绿的前提下进行。
5. 完成切片的真实前后端集成与回归；记录真实失败，不改断言迎合实现。

前期测试计划可以覆盖全部场景，不要求实现前一次写完所有测试。已授权的自主case验收按verify-delivery记录累计预算；本轮用户明确约定优先，其他专项流程仍遵从自身预算。

## 阶段 5：在测试环境开发、修复和验证

按 test-plan 区分单测、真实本地集成、mock浏览器、真实E2E、人工视觉/内容确认。各结论分别成立，不能拼接不同环境的局部成功成完整链路成功。

涉及界面时，在本阶段执行 [verify-ui](../../.agents/skills/verify-ui/SKILL.md)，复用 [测试计划的UI对照记录](templates/test-plan.md#ui对照记录)。固定全局与模块设计来源，在相同条件下查看设计/正式页面成对截图，记录和修复差异，再在测试部署复核。范围内没有未解决偏差，或已有明确接受依据并复验后，才报告UI通过；不以截图存在、功能绿或“产品尚未确认”代替研发对照。功能验证、UI对齐、产品验收分别记录；纯后端/文档无可见影响可说明不适用。

使用真实 case 时，不自动重复有成本/副作用任务；先查是否已有对应结果。说明文件输入、实现提交、任务/产物、实际输出和差异。在已授权测试环境完成本轮真实路径与相关回归；失败返回实现步骤修复，再验证受影响部分。没有相关环境或真实依赖时明确阻塞，不能请求用户把未执行当通过。

Agent负责执行前制定独立预期、测试、定位和修复，按[verify-delivery](../../.agents/skills/verify-delivery/SKILL.md)自主闭环。默认最多10轮或2小时，以先到者为准；预算内不反复交回常规失败，达到上限仍未完成时回报已验证case、差异、轮次/耗时和需用户决定的事项，通过已核验飞书本人通道通知。任务/会话切换不重置累计记录。全部本轮case实际通过后，交用户最终复核；未覆盖PRD项单列，不宣称整个产品全部通过。

## 阶段 6：飞书请用户验收测试版本

通过notify-project向用户绑定的飞书私聊发送测试入口、固定版本、已完成范围、具体验收动作、结果和限制，明确“仅测试环境可用，尚未发布staging，需要你确认”。默认群可同步待验收摘要，但群消息不能代替私聊。

等待用户本人或明确授权的决定人针对本轮版本答复。记录消息/答复来源、需求、测试版本、范围与时间；“收到”、已读、无人反对、CI绿或PR合并都不等于批准发布。用户指出问题时回到测试环境修复和重测，再请其确认，不绕过等待直接发布。

确认后版本或用户可见行为发生变化，核对影响并重新验证/确认受影响部分；纯记录修改不改变已确认制品时不重复整轮验收。缺收信机制则请用户在当前聊天明确回复，记录同样依据，不假装已自动监听飞书。

## 阶段 7：用户确认后发布staging

由release-staging检查测试验收记录、待发布制品和实际目标，再按已有PR/合并/部署规则执行。这里的staging是测试验收后的发布目标，不是个人测试环境，也不代表production已发布。不能因过去允许自动部署测试机而推定本轮staging已获确认。

确认绑定实际代码/制品及需求范围；部署步骤不得夹带未测试的新功能或最新main。构建配置、数据库和外部依赖差异按现有发布要求核对。staging完成真实业务验证后记录实际运行版本，失败先报告并按已有恢复方案处理，不以服务healthy代替业务成功。

## 阶段 8：底稿刷新

这是从正式界面到设计环境的单向移植，不是整个目录覆盖。正式入口/鉴权/后端 client 与设计入口/mock 需要保留差异；两边没有共享业务页面源码。

先列复制、转换、保留项和未交付设计；若冲突，只暂停冲突路径，提供可查看的同步差异。实际同步脚本需要根据本仓构建/路由/资源方式编写并测试，本包没有提供一个假装通用的 rsync 命令。

## 阶段 9：最后发送IM交付通知

上线流程收尾顺序固定为：用户测试验收确认 → staging发布及验证 → designend底稿同步与验证 → 补齐交付记录 → 向用户和默认项目群分别发送IM交付通知。通知由调度Skill最后调用notify-project；测试待验收通知在阶段6发送，不能与最终完成混淆。

消息说明：实际环境与运行版本、用户可用内容、访问入口、PR、真实验证范围、底稿同步结果和遗留项。PR已提交/已合并不能代替实际上线；源码测试或部署命令成功不能代替上线后验证。

发送后分别核验私聊与默认群回执。一路失败或未绑定时只保留该路待完成，不重发已成功的另一路，不重跑已通过的发布/同步；超时结果未知沿原请求核对，不换key盲重发。默认群在项目级绑定后复用，每次不重新问群，但发送前仍核验身份/目标。

只要求代码/PR而未授权上线的任务，不为发送这条通知自动部署，也不冒充“上线完成”。用户明确要求的提前评审/待验收通知如实标明状态；默认的最终交付通知仍在上述收尾最后发送。

需求疑问、阻塞、实质失败与等待提醒属于过程中必要的沟通，发生时发送，不能为了“最后通知”一直隐瞒。发布验证或底稿同步被阻塞时先报告问题，不能提前发整体完成通知；真实已上线与尚未完成项分别记录。

## 中断、恢复与变化

- 任务记录只保留当前阶段、固定来源、已完成证据、剩余阻塞、下一步；不用聊天记忆替代。
- 接到继续任务时检查实际源码/产物是否符合记录，不盲信“已完成”。
- 新设计提交不自动替换本轮已交接设计；明确是否纳入本轮。接口/测试预期随被接受的变更一起更新。
- 遇到冲突输出位置、依据、影响、建议和可继续项。所有步骤已满足的局部修复不重新走完整产品设计流程。

## 需求积累、澄清和IM交接

- 当前文档/历史需求/大文件分别按 [文件生命周期](file-lifecycle.md) 管理；关闭任务回写当前模块来源，不把几百份旧提案默认加载。
- 调查后仍有影响方向的决定时，执行clarify-task并实际读取宿主grill-me；逐项问清，未答不自行取默认方向，只暂停依赖部分。
- 群通知与提醒按 [通知约定](notifications.md) 执行，发送复用宿主feishu-messenger。问题、设计交接、待验收和实际交付只通知有意义的变化；不同渠道答案回写同一task。
- 未绑定群或没有调度能力时如实报告，不把“模板里写了”说成“机器人已经在后台工作”。
