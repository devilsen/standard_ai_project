# 怎样采用而不破坏现有仓库

1. 在现有工作分支中比较根/目录 AGENTS.md，合并职责约定，保留现有部署、数据库、客户、安全和Git规则；遇到冲突先解释，不整文件覆盖。
2. 采用本包的独立 frontend/designend 边界。现有代码迁移是另一项实现任务，要先检查构建、路由、资源、依赖与测试；本包没有执行该迁移。
3. 将任务模板合入现有文档目录，已有 PRD/case/计划只引用。记录中相对路径以实际项目根为准。
4. `.agents/skills` 是项目技能交付位置。宿主支持项目技能发现时直接使用；不支持时显式读取对应 SKILL.md，或按宿主规范安装副本。不要声称仅复制目录就已验证自动发现。
5. Skill 中的 `../../../docs/workflow/...` 是相对本包项目布局的链接；若将 Skill 单独安装到个人全局目录，应改为项目资源定位，不把原相对路径直接搬走。
6. 从现有 package.json、pyproject、CI 和测试配置发现实际命令，在每项任务的命令表中写工作目录、命令和依赖。缺环境或服务地址要明确记录。
7. 自动检查先以现有命令组合实现。导入边界、mock网络隔离、OpenAPI一致性、发布来源分离、底稿同步检测是后续需实现/验证的检查，当前模板没有部署它们。
8. 若需要 PR required checks / 分支保护，由仓库现有权限与规则配置；不能靠 AGENTS.md 宣称已拦截绕过。
9. 先用一个模块试运行：保留基线Skill版本、运行评估任务、按评分表记录行为和证据，修订后再考虑推广。
10. 需求文件沿用已有路径；新任务可采用按年job布局，当前模块来源和长期测试复用原位置。不要批量移动旧任务或自动清理证据。
11. 确认宿主grill-me、feishu-messenger可用。它们是外部技能依赖，不复制进本包；缺失时明确缺口，不假称调用成功。
12. 按[配置示例](project-settings.example.json)一次登记测试与staging环境、发送身份、用户私聊与默认群绑定引用、授权事件和决定人。真实绑定存私有配置；本包尚未绑定目标，也未发送消息。提醒阈值、实际调度和收信能力另行接入，不能仅靠规则文件承诺。
13. 各模块README保留为面向人的入口，采用后补充实际运行/访问方式。新建模块或改变入口时同步维护；当前模板没有业务应用，不把计划中的命令写成已可执行。
14. 接口定义集中在apiend/contracts，apiend负责统一入口与展示。本模板已完成该目录合并；目标项目若已有其他路径，迁移时核对调用方和生成配置，不直接移动外部仓库文件。

15. 交付顺序采用“测试环境开发修复与验证→飞书私聊请用户验收→明确确认该版本→staging发布验证→底稿与记录→最后私聊及默认群通知”。记录确认来源和实际制品，测试绿或沉默不解锁staging；已确认同一版本不重复询问。

## 建议先落地的最小集合

- 根与实际涉及目录的规则。
- 调度Skill和当前阶段Skill。
- 一份任务记录，引用固定设计/PRD/case/接口。
- 已有模块测试与明确的真实案例验收。

模板里的角色、目录和测试示例不代表必须新增同名职位、服务或文件。选择适用部分并说明已有等价物，避免为了遵循流程而重复建设。
