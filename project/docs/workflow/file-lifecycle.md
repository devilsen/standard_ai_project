# 几百个需求之后怎样维护文件

原则：当前有效内容按模块维护，历史过程按需求保存，大体积材料使用已有受管存储。数量增加不等于每次读取所有历史，也不等于每个需求新增一组长期规则。

## 推荐布局

```text
docs/spec/
  domains/
    assembly/                 # 当前有效行为/设计；已有正式来源则直接引用
    materials/
  jobs/
    2026/
      REQ-0123-adjustment/
        task.md               # 来源、进度、决定、证据与关闭状态
        ...                   # 只有确有需要的变更说明/切片/测试计划
    2027/
      REQ-0345-materials/
apiend/contracts/assembly/     # 当前接口，历史由Git保存
cases/assembly/                # 可复用代表案例，敏感原件在授权存储
frontend/.../tests/            # 当前行为测试
backend/tests/.../             # 当前业务与对接测试
e2e/assembly/                  # 当前浏览器/真实case测试
```

这是待采用布局。已有job目录不为统一命名批量搬迁；记录沿用旧路径即可。需求ID优先使用现有Issue/需求系统标识；没有才选本地唯一名称，不另建一套重复编号平台。

## 当前与历史的关系

| 内容 | 长期放在哪里 | 需求结束后怎样处理 |
|---|---|---|
| 已接受行为/规则 | 当前模块正式来源 | 合并本次已接受变化，历史过程仍保留 |
| 本轮提案、决定、进度 | 对应job | 标记closed或cancelled，固定路径保存 |
| API | apiend/contracts原模块 | 更新当前契约，旧版本由Git追溯 |
| 测试 | 模块既有测试集 | 保留有价值回归；删除过时测试需有行为变化依据 |
| case | cases原模块 | 复用/补充代表案例，不为每次重复复制原件 |
| 图片、Word/PDF、录像、大日志 | 现有授权存储/CI制品位置 | job保留链接、摘要、访问范围和已有留存策略 |
| AGENTS和Skill | 模块/工作流原位置 | 只在职责或流程有实际变化时修改，不每需求生成一份 |

若项目的正式产品来源在其他仓库，本仓domain目录只保存入口引用，不能把新摘要变成并行权威。没有获得产品确认的提案不写入已接受模块规则。

## 日常读取

1. 先读当前模块正式来源、本次task、直接依赖和适用规则。
2. 历史问题按需求ID、模块名或关键词用rg定位，再读取命中的相关部分；不把几百份task和旧PRD全文加载。
3. 多轮产品方案由固定交接提交定位；当前任务不自动采用历史文档或最新未交接版本。
4. 当前工作列表从task状态生成/查询，或沿用现有Issue系统；不手工维护另一份可能过期的进度总表。

关闭记录不反复移动，因此链接稳定。已有链接发生调整时一并检查引用；不为“归档”统一改写历史证据。

## 关闭与回收

关闭时核对：请求范围已交付或用户取消；当前行为/测试/case已回写；未执行和剩余问题有明确去向；PR/发布/验收真实状态正确；用户测试确认、staging实际版本及私聊/默认群各自通知状态已记录。未确认时停在待验收，未发完时保留待通知，不能虚构整体完成。仅有PR或代码完成，不代表真实验收已完成。

关闭是记录状态，不删除资料。未被用户接受的部分不被强制宣称完成；可将明确剩余工作引用到后续任务。纯代码交付任务无需为关闭而额外发布。

大文件不提交Git，敏感内容按原权限保留。没有既定留存策略时先说明存储与保留取舍，不擅自按30/90天删除。临时worktree、构建缓存按项目已有清理规则处理，先确认未交付工作；不能因任务closed就强删。

## 本模板没有做的事

没有移动现有需求、删除文件或配置对象存储生命周期；也没有新建索引数据库。未来若需要自动生成工作列表，先复用现有Issue/CI/文档工具。
