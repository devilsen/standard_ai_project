# 测试验收后发布staging

读根规则、实际发布/数据保护规则、task/delivery、用户验收来源和环境配置。测试机与staging身份分别核对，不能从“服务可访问”或过去测试部署授权推定发布许可。

## 步骤

1. 检查测试环境本轮验收项通过，用户本人/明确授权决定人已确认该需求、版本和范围。缺确认时交回verify-delivery等待，不能自行批准，也不重复要求已存在的同一确认。
2. 比较待发布代码/制品与已确认版本。不得夹带最新main或未经测试的修复；有行为/制品变化时返回测试环境验证和相应用户确认，纯记录变化不自动使原制品验收失效。
3. 按现有PR/合并与发布规则准备固定制品，核对测试与staging配置差异、迁移、在途任务、数据保护及恢复方案。仅本轮staging目标，不扩展到production。
4. 在授权范围内发布，核对实际运行版本，回放本轮真实关键业务和历史兼容。health/200不代替业务验证。失败报告具体事实并按现有恢复方案处理，不能盲目循环发布。
5. 记录staging入口、版本、验证和限制，交回project-workflow继续refresh-design；补齐交付记录后最后分别通知用户和默认项目群。

## 完成

仅声明真实达到的发布/验证状态。通知失败不要求重发部署；发布失败不能发送最终成功消息。发布记录与测试确认分别保留，供换会话恢复。
