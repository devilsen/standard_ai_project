# 项目IM通知

读 [通知约定](../../../docs/workflow/notifications.md) 和本task的绑定引用。共享Skill不保存真实账号、群、密钥或个人偏好。

## 发送条件

测试环境验证通过后必须私聊用户请求该版本验收，明确尚未发布staging。最终通知位于最后：用户确认→staging发布及验证→designend底稿同步/验证→交付记录→本Skill分别通知用户与默认项目群。不能在提PR、测试通过或刚部署时宣布整体交付完成。

关键疑问/阻塞、实质失败和已约定等待提醒在过程中及时发送；设计评审按实际需要发送。每条内部测试或重复状态不发送。默认群和用户接收者从项目配置的私有绑定引用读取，缺失时不能猜测。

用户对项目群和阶段的持续授权覆盖同范围发送，不逐条重复索取同意；未指定群、身份/项目不匹配、扩大接收人或内容披露范围时不能猜测目标。

## 步骤

1. 核对事件和产物。测试验收消息要求测试环境本轮通过且有准确入口/版本；最终消息要求用户确认、staging验证、底稿和记录完成。缺项报告阻塞，不发成功消息。内容包括实际环境/版本、PR、验证/限制、具体下一步，测试消息明确等待确认且未发布staging。
2. 从宿主技能目录定位并读取 `feishu-messenger`，按其当前身份、接收者、文风和发送流程执行。缺工具/绑定时报告未发送，不创建新应用、自动OAuth或改用他人账号。
3. Agent通知默认用本人的已绑定bot；核验当前身份、用户私聊接收者和默认项目群。遵守messenger实际支持的发送方式，不冒充人或改用别人的账号。实际请求与收据在私有目录，task不保存凭据。
4. 以需求ID、阶段、问题/交付版本和接收者识别事件，先检查回执。测试通知必发用户；最终通知分别发用户和默认群，逐路冻结、去重与记录。一路已成功不能因为另一路失败而重发，默认群已绑定不逐次重新询问。
5. 超时/中断时标记结果未知，沿原request_id核对，不换新请求盲目重发。平台接受但回读无权限时记“已接受，回读未验证”，不因缺回读重复发送。
6. task分别记录私聊/群message_id与验证状态。缺绑定/权限或发送失败时报告具体缺口，不用群@代替私聊。通知不改变测试或发布结果；用户未确认仍不得发布staging，不因缺消息通道自行推定同意。

## 提醒与答复

已发问题尚未解决且达到约定时间时，可发一次提醒；持续未变化不反复发送。依靠已配置的宿主自动化/可恢复执行，不假装SKILL.md自身是后台服务。不因群收到消息就改变决策状态；答复经授权身份确认后回写原task。
