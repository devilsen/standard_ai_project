# UI 设计对齐检查

## 开始与范围

读取项目规则、现有task、设计交接和测试计划。复用已确认的设计版本、范围与授权；说明本次检查哪些页面、状态和部署版本，随后直接收集证据，不重复请求已给出的确认。本Skill是workflow第5步内的UI子流程，不新增审批，不替代功能测试或用户验收。

仅检查受影响的界面；共享组件、导航或样式有变化时包括受影响的代表性页面。纯后端/文档改动且没有用户可见影响时，在原任务记“不适用”及依据，不强制运行截图。用户只要求检查时提交差异，不自动修改实现；已有修复授权时继续修复和复验。

## 1. 固定对照依据

- 在 [测试计划的UI对照记录](../../../docs/workflow/templates/test-plan.md#ui对照记录) 中引用已确认的设计提交/截图、PRD、品牌token、测试环境和实际实现版本。分别注明全局框架与本轮模块的设计来源，不混用历史原型或未交接的新稿。
- 从已有交接和获准来源自行取得设计并实际查看；缺访问或缺关键设计时明确对应未验证范围，其他检查继续。不能用当前实现截图建立设计基准，也不能猜测缺失设计并宣称对齐。
- 列本轮主路径和相关空、加载、错误、未完成、长内容、浮层、历史状态，按实际改动取舍。覆盖项目要求的桌面与窄屏；没有约定时可用1440px和390px作检查视口，并注明是检查条件、不是新增产品断点。

完成条件：每个待检查场景有可追溯设计来源、操作与显示预期；未覆盖或设计未明确的项可识别。

## 2. 获取可比较的画面

- 运行固定设计场景和正式页面，复用项目浏览器工具；本项目使用Playwright时按已有启动方式执行。没有可用浏览器时记录未执行，不以源码阅读冒充截图检查。
- 同一场景保持语言、主题、视口、缩放、字体加载、数据长度、滚动及展开状态一致，等待加载/动画稳定。保留设计图和实现图的配对链接、入口、状态、时间及实现版本；叠图/像素diff按定位需要使用，不设任意相似度百分比代替判断。
- 同场景数据优先复用隔离样例或受控API回放。明确标注mock、预置、真实依赖；受控场景证明呈现，不证明真实模型/后端成功。交付前在实际测试部署复核受影响页面；场景在部署中不可达就记缺口，不能用本地回放冒称部署已验证。
- 不为截图擅自重跑模型、上传资料或写共享环境。必要写入沿项目授权使用隔离数据库和文件存储。动态时间等差异单独说明；不得遮盖错位、关键文案、分数或控件来制造一致。

完成条件：选定场景有可直接查看的成对截图和复现条件；缺图、不同数据或替身的影响已写明。截图与业务内容按项目已有私有存储/脱敏规则保存，Git只放允许公开的记录与引用。

## 3. 逐项对照与交互检查

实际查看成对截图，不能只检查文件存在。按以下顺序记录偏差，不能用“看起来差不多”收尾：

1. 结构与位置：导航、信息层级、区块顺序、主次操作、表格列和浮层位置。
2. 尺寸与间距：容器宽度、密度、对齐、留白、按钮/输入框尺寸及遮挡。
3. 字体与颜色：字族、字号、字重、行高、token、边框、圆角、图标与状态标识。
4. 文案与状态：标签、提示、单位、缺件/限制说明及显示隐藏；真实数据变化不应被误判为布局许可。
5. 交互与响应式：点击/切换/返回/刷新、焦点与键盘、滚动/折叠/窄屏，核对操作前后与设计相符；不能以无横向溢出代替全部检查。

差异表逐项记录：场景与元素、设计预期、实现实际、成对证据、影响、处理决定和复验结果。即使没有发现差异，也记录实际检查范围及上述维度。设计未覆盖的真实状态按PRD核对并单列，不能写成已与设计一致。

## 4. 修复与复验

已有授权内修正实现，再用相同条件重截受影响场景，回归对应交互；共享改动检查其代表性调用页。复用项目修复轮次规则，不额外新增次数或审批。

需要改变已确认设计/产品语义时，展示具体差异与原因，按 [clarify-task](../clarify-task/SKILL.md) 只询问未解决的决定。已有明确接受差异的决定直接引用，不重复确认。不得改参照稿、放宽预期、更新基准图或把偏差记为“不适用”来迎合当前实现；设计变更获准后固定新依据并复验。

## 完成与返回

将记录留在原测试计划/任务中，已有等价表格直接复用，不再建立独立看板。每个场景注明通过、存在差异、未执行或不适用；范围内所有适用场景均已检查、无未解决偏差，或偏差已有明确接受依据并已复验，才能写“本轮UI对齐通过”。接受的差异仍在交付中明列；缺设计/环境/证据时不宣称100%对齐。

在 [交付记录](../../../docs/workflow/templates/delivery.md) 中分别报告功能验证、UI对齐、产品验收。用户尚未确认不代表研发可省略UI自检；截图相似或功能绿也不代表产品已验收。完成后返回 [verify-delivery](../verify-delivery/SKILL.md)，第6步的常规待验收通知应携带已完成的UI结论；有未解决项时发具体缺口，不以“UI已通过”交给用户常规找差异。本Skill不授权发布或对外通知。
