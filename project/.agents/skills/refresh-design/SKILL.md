# 更新设计底稿

## 输入与首次检查

读designend/mockend规则、实际发布记录、来源frontend提交和设计工作区。确认用户测试验收、staging实际运行版本及业务验证有证据；不能用测试环境版本或最新main代替实际发布来源。检查Git差异、已交接版本、未交付设计与下一轮设计。

## 步骤

1. 明确同步范围：页面、组件、样式、资源；保留项：设计入口、mockclient、场景工具和本地配置；不带入项：凭据、真实用户资料和正式部署配置。完成条件：复制/转换/保留清单有实际路径。
2. 预览差异与冲突。未交付设计不能覆盖；保留它的工作分支/提交，提出逐项合并方案。只有需用户决定的冲突等待答案，非冲突部分可继续准备。
3. 从固定上线提交移植界面，按独立设计环境需要适配mock。现有同步脚本可复用，否则先设计/测试本项目的转换；不把全目录rsync或删除重建当作通用办法。
4. 验证设计可启动、关键路由、代表性正常/异常场景、视觉对应及没有业务后端请求。完成条件：它是可操作的mock底稿，而不是一个偷偷连接真实后端的frontend副本。
5. 按项目Git约定保存同步差异，记录来源发布提交、设计交接保留位置、同步结果与限制。

## 完成

新底稿来源清楚，原设计没有丢失，frontend和designend仍各自维护页面代码。单测或mock浏览器通过只证明本次底稿刷新范围，不重新宣称生产验收。把同步验证与差异回写交付记录后交回project-workflow，最后进入notify-project；本阶段不提前宣布整个工作流结束。存在未解决同步冲突时报告阻塞，不能用成功通知掩盖。
