# 按行为拆分、测试与实现

## 开始

读本任务实际修改路径的规则、固定设计/PRD、case、接口及现有实现/测试。先确认用户要计划还是实现；计划授权不扩展为代码、发布或外部写入授权。

## 先计划

1. 使用 [测试计划](../../../docs/workflow/templates/test-plan.md) 将每项行为对应到独立预期、公共测试边界和需要的验证层。界面交互用组件/浏览器，业务规则用单测，数据库/存储用真实集成，完整case留真实E2E。完成条件：关键行为与异常有实际验证方法，mock边界明确。
2. 用 [切片模板](../../../docs/workflow/templates/slice.md) 划分最小可演示行为；每片包含完成该行为所需的UI/API/后端/测试。已有能力不重建；数据迁移或准备工作只有能独立验证且确为依赖时单列。完成条件：新Agent仅凭切片及引用即可执行，没有隐藏产品选择。
3. 列真实依赖、当前可开始的切片、改动范围和风险。避免“全部前端完成→全部后端完成→最后联调”。完成条件：用户知道先看到什么结果，每片怎样完成。

## 实现授权存在时逐片执行

4. 选本片一个可观察行为，写一个测试并运行。确认失败因为目标行为未实现，环境错误不算有效Red。
5. 写足够通过的最小实现，聚焦测试和类型/静态检查通过后再处理下一行为。不要一次写完所有测试或提前建设通用平台。
6. 检查代码职责、重复、依赖与公共影响；保持测试为绿再做有依据的小重构。新增产品限制/关键交互/数据含义先明确提出，不用技术理由默默引入。
7. 完成本片真实前后端集成，执行受影响回归；环境不足记录限制，不用mock通过替代。完成条件：本片的可观察结果和必要失败行为有证据。
8. 更新任务进度、实际命令、已运行结果与下一片。模块用途、入口或使用方式变化时更新其README，新模块补齐面向人的简短入口。新范围变化及时写回，不修改既定预期来迎合实现。

## 完成

计划任务交付依赖有序的切片与测试矩阵；实现任务交付代码、对接/单测用例和证据。遵守项目已有变更体量、审查和自动修复限制；没有新问题不重复扩大测试。发布交付转入verify-delivery，而非自动宣布上线。
