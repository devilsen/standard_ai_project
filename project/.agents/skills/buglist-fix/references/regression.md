# Bug回归测试晋升

修复一次Bug应判断如何防止再次出现，不把所有Bug都变成完整E2E。每Bug将决定写入bug.md，PR说明新增/更新/复用测试与实际覆盖。

## 何时保留长期测试

满足任一项，应新增、更新或核验复用长期回归：影响主流程或核心输出；同类问题已有至少两次记录；修复后再次回归；涉及权限、数据丢失、文件损坏、金额或内容错误；用户易触发且影响大；暴露稳定接口或状态合同缺陷。重复发生须引用历史Bug，不能凭印象计数。

已有测试没发现问题时检查断言、输入、任务发现和触发范围，而不是再写一个相同测试。用确认预期断言可观察行为，验证能识别旧错误，不以私有实现、当前快照或固定模型措辞当正确性来源。

## 放在哪一层

| 行为 | 优先保护位置 | 交付补充 |
|---|---|---|
| 规则、状态、计算与转换 | 单测 | 关联主流程才补交付Case |
| API、权限、事务、持久化与协议 | 契约/真实本地集成 | 涉及历史数据时核验存量兼容 |
| 点击、导航、错误呈现与恢复 | 组件或定向Playwright | 明确设备/视觉标准和人工项 |
| 跨前后端主流程、生成与文件内容 | 最近边界的快速回归，加隔离E2E | cases原业务模块维护输入、预期、允许差异和失败条件 |

测试可直接引用原模块既有用例；cases保存长期代表性业务验证，不为每Bug复制真实原件。Bug记录关联测试/Case ID；测试或Case也以项目现有方式关联Bug或已确认行为，需求变化时一并维护。

## CI/CD如何接入

先检查现有命令、测试发现配置、路径过滤和任务触发；不能把测试文件存在当CI覆盖。按实际风险分配快速单测/契约/组件到PR，较慢浏览器回归到合适合并或nightly任务，完整真实交付Case到发布前受控验证。频次是选择依据，不要求每个项目新增三套重复流水线。

有现成任务就接入其发现/选择范围，在相应改动PR中验证用例数量、失败退出码和实际执行证据。需新建自动任务时沿用仓库CI规则与授权；不能借此自动部署、自动合并或新增发布审批。记录工作流路径、job、命令、触发条件和实际run链接；没有接入则明确未接入，并留下接入待办。

采用时读取目标项目实际CI配置与E2E执行入口；本模板不包含业务流水线，不推定任何测试已接入。敏感凭据、真实业务文件不得进入PR测试；共享staging只读，写入/生成Case使用隔离数据库和文件存储。

## 暂不能自动化

一次性脏数据、偶发外部故障、未确认视觉预期或只能依赖特定客户文件，先判断能否提炼稳定的错误处理/恢复合同。能覆盖的部分仍应覆盖，真实服务未验证单独报告。确无稳定断言时记录原因、人工步骤、证据和下一步，不虚构自动通过；这不构成Bug已验收或取消必要交付验证。

失败、跳过、空套件和mock-only各自报告。不要通过重试、放宽断言或修改预期消除失败；不增加没有新证据的无限复测。晋升是修复过程的一部分，不重置每Bug两轮实现预算。
