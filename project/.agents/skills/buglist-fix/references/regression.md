# Bug回归测试晋升

修复一次Bug应判断如何防止再次出现，不把所有Bug都变成完整E2E。每Bug将决定写入bug.md，PR说明新增/更新/复用测试与实际覆盖。

## 何时保留长期测试

满足任一项，应新增、更新或核验复用长期回归：影响主流程或核心输出；同类问题已有至少两次记录；修复后再次回归；涉及权限、数据丢失、文件损坏、金额或内容错误；用户易触发且影响大；暴露稳定接口或状态合同缺陷。重复发生须引用历史Bug，不能凭印象计数。

已有测试没发现问题时检查断言、输入、任务发现和触发范围，而不是再写一个相同测试。用确认预期断言可观察行为，验证能识别旧错误，不以私有实现、当前快照或固定模型措辞当正确性来源。

## 放在哪一层

| 行为 | 优先保护位置 | 交付补充 |
|---|---|---|
| 规则、状态、计算与转换 | 单测 | 关联主流程才补交付Case |
| API、权限、事务、持久化与协议 | 契约/真实本地集成 | 涉及历史数据时核验存量兼容 |
| 点击、导航、错误呈现与恢复 | 组件或定向Playwright | 明确设备/视觉标准和人工项 |
| 跨前后端主流程、生成与文件内容 | 最近边界的快速回归，加隔离E2E | cases原业务模块维护输入、预期、允许差异和失败条件 |

测试可直接引用原模块既有用例；cases保存长期代表性业务验证，不为每Bug复制真实原件。Bug记录关联测试/Case ID；测试或Case也以项目现有方式关联Bug或已确认行为，需求变化时一并维护。

## 真实业务验证由代理完成

涉及页面或跨模块业务结果时，代理把已有局部回放接入固定提交的正式 frontend、真实后端及隔离存储，执行以下链路。纯后端问题按实际公共接口验证，不为凑形式增加页面测试。

1. **固定预期**：从原Bug、截图、原件和已确认回复提取前置状态、操作、期望结果及失败条件，写入原bug.md并引用来源；不能从当前实现反推正确答案。仅对影响结果且无法查明的业务歧义询问用户。
2. **准备原始输入**：在独立数据库和文件目录中预置该Bug必需的原文件、关联记录、版本及历史任务结果，核对文件哈希与对应关系。只取必需数据，关闭无关worker、模型及通知；不默认全库复制、覆盖现有测试库或写入共享staging。预置历史结果须显式说明，不能冒充重新生成成功。
3. **从正式入口操作**：走实际页面、API和存储完成原操作，不用内部函数直调或API mock冒充业务页面验证。原问题需要生成/装配/导出时按确认范围验证最终结果；仅需已有产物读取时不擅自重跑昂贵生成任务。
4. **检查业务结果与持久化**：按独立预期核对页面显示、目标页/内容、必要的下载文件及接口结果，保存后刷新或重新进入确认。稳定行为用Playwright断言，版式、章位置等视觉问题对照原件；截图、2xx或文件存在不能单独算通过。原生控件的程序填值不能冒充面板内点选。
5. **记录真实边界**：在原bug.md保留固定版本、入口、输入来源、预期来源、实际操作、结果、证据及真实/预置/替身边界。失败记录具体停点并追溯责任Bug及累计轮次；环境重试与实现新方案分别计数。

局部单测、文件字节或数据修复回放仅证明对应边界，不能据此宣布完整业务通过，也不能停在“待补完整页面”而没有继续执行。未复现时继续核对原路径、状态、版本及环境；新建正常案例可作对照，不能替代原失败场景或将Bug标为已解决。遇到真实阻塞如实报告并继续独立项，不以用户对照或最终验收替代代理可自行完成的测试。整批真实验证完成后，再提交准确测试版本供用户确认；确认前不发布staging。

## CI/CD如何接入

先检查现有命令、测试发现配置、路径过滤和任务触发；不能把测试文件存在当CI覆盖。按实际风险分配快速单测/契约/组件到PR，较慢浏览器回归到合适合并或nightly任务，完整真实交付Case到发布前受控验证。频次是选择依据，不要求每个项目新增三套重复流水线。

有现成任务就接入其发现/选择范围，在相应改动PR中验证用例数量、失败退出码和实际执行证据。需新建自动任务时沿用仓库CI规则与授权；不能借此自动部署、自动合并或新增发布审批。记录工作流路径、job、命令、触发条件和实际run链接；没有接入则明确未接入，并留下接入待办。

本仓目前.github/workflows/light-check.yml只做选定Python路径lint，不能当单测、前端或E2E已覆盖。现有隔离浏览器与定时器入口见e2e/DEVELOPMENT.md，脚本存在不代表目标主机定时器已启用。敏感凭据、真实业务文件不得进入PR测试；共享staging只读，写入/生成Case使用隔离数据库和文件存储。

## 暂不能自动化

一次性脏数据、偶发外部故障、未确认视觉预期或只能依赖特定客户文件，先判断能否提炼稳定的错误处理/恢复合同。能覆盖的部分仍应覆盖，真实服务未验证单独报告。确无稳定断言时记录原因、人工步骤、证据和下一步，不虚构自动通过；这不构成Bug已验收或取消必要交付验证。

失败、跳过、空套件和mock-only各自报告。不要通过重试、放宽断言或修改预期消除失败；不增加没有新证据的无限复测。晋升是修复过程的一部分，不重置每Bug五轮实现预算。
