# 单个 Bug 本地记录模板

每个 Bug 必须有一个独立目录：`docs/spec/jobs/<year>/<BUG-ID>/`。结构化事实保存bug.json（阶段、时间、归因、轮次、里程碑与链接），按[漏斗约定](funnel.md)维护；`bug.md`只保留下面的人可读调查说明，重复的状态/轮次/交付字段改为引用JSON，不维护第二份可编辑状态表。文件名固定为 `bug.md`；截图、脱敏样本和日志放该目录的私有或被忽略证据目录，不把敏感原件提交 Git。

```markdown
# BUG-ID：简短标题

工程事实见同目录 [bug.json](bug.json)：来源、阶段、轮次、归因分类和交付链接只在那里维护。本文解释观察、推理与验证边界。

## 现象与预期

### 用户实际看到的现象

<!-- 只写截图、录屏、日志或用户描述中能证明的事实。 -->

### 期望结果

<!-- 标注来源：用户确认 / PRD / 已有用例 / 待确认。没有来源就写待确认。 -->

### 复现条件

- 环境与版本：
- 输入数据/文件版本：

- 复现结果：
- 复现等级：A原环境 | B隔离真实数据 | C最小样本 | D合同级模拟 | E证据诊断 | F证据不足

- 已证实根因：
- 证据链接：

## 修复说明

按bug.json中的实际round编号追加说明，不预建两份状态表：

- 为什么选择这个方案，排除了什么：
- 改动如何消除根因：
- 失败观察与下一步调查（若有）：
- 证据解释及验证范围：

## 回归测试晋升

- 决定：新增 / 更新 / 已有覆盖复用 / 暂不自动化 / 不适用
- 依据与关联Bug：主流程 / 同类重复至少2次 / 修复后回归 / 高风险 / 稳定契约 / 其他
- 行为与预期来源：
- 长期测试层级、文件及具体用例：
- 修复前失败/修复后通过证据（未执行说明原因）：
- 交付Case路径与ID、预期和允许差异（不适用说明）：
- 执行入口：工作目录、命令、选择条件或标签：
- CI/CD任务路径及job：未接入 / 已配置未验证 / 已运行验证
- 触发时机：PR / 合并 / nightly / 发布前 / 人工受控
- 实际执行链接/结果、跳过项与限制：
- 外部服务、隔离数据与成本/稳定性：
- 暂不自动化的原因、人工验证步骤和待办：

## 验证边界

交付里程碑、版本与证据链接见bug.json。这里说明哪些真实行为已验证、哪些只在模拟层验证、哪些尚未执行，以及对交付判断的影响。

## 阻塞与交接

- 缺失数据/权限/截图：
- 需要用户决定的问题：
- grill-me记录：
- 五轮耗尽后的建议：
```

记录原则：每次读取、复现、修改、测试、PR和状态变化都追加事实；不覆盖失败历史，不用“已修复”替代证据，不把未复现写成修复失败。
