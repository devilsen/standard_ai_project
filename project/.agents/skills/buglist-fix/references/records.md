# Bug执行与来源回写

JSON工程事实与Markdown说明按[结构化归因与漏斗](funnel.md)维护；下面字段映射到JSON或说明，不重复双填。同一Bug跨会话使用原路径，阶段变化触发本地校验和漏斗同步。

## 任务最小记录

沿用原Bug job；没有才在既有docs/spec/jobs下按项目约定建立，不另复制整份buglist。

| 项 | 内容 |
|---|---|
| 来源 | 清单链接/本地路径、稳定Bug ID、原记录/块/单元格标识、截图与附件入口 |
| 行为 | 用户预期来源、实际现象、最小复现、环境与版本、观察到的根因及证据 |
| 领取 | 现负责人、领取动作与回读；无写入能力明确本地执行状态 |
| 轮次 | 累计0/1/2；每轮分支/起点、假设、修改、命令、结果和失败原因 |
| 数据 | 样本来源与授权、脱敏与隔离位置；不记凭据/敏感原文 |
| 回归 | 晋升依据、长期测试与交付Case ID、真实执行入口/CI job及证据；未接入明确说明 |
| 交付 | 唯一PR与head提交、定向验证、原“关联技术交付PR”值与回写回读 |
| 等待 | 关键疑问、grill-me结果、两轮失败的交接、可继续项 |
| 集成 | 纳入的固定提交、整批case结果、用户确认来源、staging实际版本、通知状态 |

首次仅记录已知项，后续逐步补充，不每Bug生成大量重复文档。任务只是执行记录，正式产品决定和原清单状态保留原来源。

## 截图和staging取样

飞书资源先确认Docx/Sheet/Base类型、访问身份和实际读写能力；使用宿主已有正式工具，不臆造API/CLI参数。没有工具只阻塞访问/回写，不自动安装或借用其他身份。若采用feishu-triage-bug-owner，先读其当前策略；本批用户指定的清单与关联技术交付PR仍是明确回写目标，不未经要求迁移Bug平台或批量新建Issue。

截图需实际打开查看。若是内嵌图片或附件token，按原资源权限取出并核对对应Bug；不可访问时记录缺失，不把OCR推测当产品预期。

取样记录实际环境和时间、所需资源ID、关联文件/版本、脱敏方式、隔离数据库与文件存储；截图、原件和完整数据库快照仅留授权私有位置。staging不执行修复SQL、任务重跑或合成上传。测试依赖外部服务时说明真实/替身边界，不能把mock通过写成完整修复。

## 单Bug PR正文

```markdown
修复 BUG-ID：触发条件与修复后的可观察行为。

原因：已证实的代码/数据路径及复现证据；尚有假设则明确。
改动：具体改了什么，为什么；权限/契约/历史数据影响（涉及才写）。
验证：测试环境及固定版本、定向用例/命令、实际结果与证据。
限制：未覆盖项、存量数据是否已验证；当前未发布staging。
关联：原Bug记录链接、执行记录；依赖PR（如有）。
```

不在正文粘贴敏感业务文件、账号或密钥。失败两轮不创建伪装成“已修复”的交付PR；如用户要求保留调查PR，明确是未解决的调查，不填成成功交付。

## 写回与批次摘要

“关联技术交付PR”回写验证的是原Bug的真实链接，不能只把URL写到本地日志或聊天。链接字段遵从实际schema；保留原有有效PR，发现冲突先查是否同Bug已交付。没有写权限就保留待回写，不能宣称文档更新成功。

批次摘要只列Bug ID、结果、已用轮次、PR、源回写状态、阻塞和集成版本引用；业务结果不重复复制。领取/待验收/已发布/产品已验收按源表真实状态映射，不自行创造状态枚举或代填产品验收。
