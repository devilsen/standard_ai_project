# 归因、结构化记录与长期漏斗

## 一份工程事实，两种阅读方式

每Bug保留同一job目录；已有路径不搬迁。`bug.json`维护阶段、事件、轮次、归因与链接等机器事实，`bug.md`保留人可读的现象、调查推理与结论，并引用JSON；不要手工在两边重复维护状态、时间和轮次。旧Bug逐条按证据迁入，未知留空，不能从“改好了”推定验收成功。

原Bug清单负责报告、领取及产品决定；本地JSON负责工程事实；用户指定的漏斗多维表格是工程数据投影。产品验收仍以真实用户确认来源为依据，不能以本地文件覆盖远端产品决定。同步前核对最新原记录，同字段冲突停该字段并说明，不按最后写入覆盖。

最小数据结构见[合成示例](bug.example.json)，由[scripts/bug_funnel.py](../scripts/bug_funnel.py)校验。schema_version目前为1，保留追加事件：

- stage_entered：当前阶段及进入时间；回退再次追加，保留旧历史。
- blocked/unblocked：独立阻塞原因与下一步，不把缺数据当新阶段。
- milestone：具备证据的通过/失败/撤销，PR、定向验证、用户确认和发布分别记录。
- reopened：重开原因，清除当前成功统计但不删除旧证据或重置两轮预算；默认回到diagnosing并清除旧阻塞；若实际返回其他阶段，同时间追加stage_entered。

导入旧修复时，未知开始时间/结果保留started_at=null、status=unknown，提供historical_evidence和本次observed_at；仍计入预算，不补造时间。as-of在首次观察前不含该导入，不能据此重建历史真实预算。

每事件有稳定唯一ID、带时区时间，按时间追加；重试同一事件不重复写入。当前阶段由事件推导，不能手填另一个status。JSON不得保存真实客户原件、截图正文或密钥，只保存授权证据引用。

## 根因归因

分别记录技术原因和流程原因，category加具体说明、hypothesis/confirmed及证据。没有证据用未知空列表，不能默认归咎需求或开发。

技术分类起点：前端状态、业务逻辑、接口契约、持久化/迁移、文档处理、外部依赖、环境配置。流程分类起点：需求预期缺失、设计交接遗漏、回归缺口、测试数据不足、环境差异、诊断证据不足。允许按真实机制增补，不把分类枚举变成新的业务限制。

“怎样引入”和“为何未提前发现”分开说明；归因是可修订结论，变更记录理由与证据。开发新需求时读取本模块已确认的同类归因和回归用例，采用对应检查，不加载全部历史或增加全局门槛。

## 两个Tab与指标口径

**统计Tab**从明细/事件生成：全部Bug数、今日仍有效的定向验证通过数、今日仍有效交付数、当前阶段分布、阻塞数量、两轮耗尽数、重开数。当天按Asia/Shanghai计。当前阶段停留时长按最近进入该阶段计，包含阻塞等待；不冒充累计修复工时。

**明细Tab**每个项目+Bug ID一行：标题、来源稳定记录ID、本地记录引用、阶段、进入时间/停留、阻塞及下一步、轮次、复现等级、双重归因、PR、定向/用户/staging验证、更新时间。事件全文继续保存在本地JSON，不用覆盖最新状态丢掉过程。

总体定向验证通过率=当前有有效targeted_verified证据的Bug/全部范围Bug；另列已尝试修复中的通过率，两者同时保留分子分母。真实案例、用户验收和staging通过各自统计，不把单测绿或PR创建当整体修复。模拟层验证必须标明边界，不能登记成原Bug真实复测通过。

“今日通过”按当前仍有效的最后一次对应里程碑日期、Bug去重统计；不是提交数、事件条数或今天改过代码数量。重开撤销当前成功计数。0分母显示空值，历史材料不全不补造时间。

Skill能力还需固定skill/model/工具/批次输入，记录在本轮任务；比较相同条件下的首轮/两轮结果、各阶段转化、阻塞原因和重开，不能从一个总体百分比推出编码能力。不删难题提高成功率；看板展示的是业务结果，独立场景评估仍负责检测Skill决策。

## 本地导出与飞书接入

```bash
python3 .agents/skills/buglist-fix/scripts/bug_funnel.py --root docs/spec/jobs --output /tmp/一个尚不存在的私有导出目录
```

输出funnel.json、summary.csv、details.csv。只读本地数据，无网络写入；重复ID/非法记录会报错而非悄悄忽略。报告只覆盖root内已建JSON的Bug，必须在批次核对其ID集合等于清单范围，缺记录不能称全量漏斗。没有记录就输出0且明确尚未导入，不能填造这11个Bug。

--as-of可过滤事件到某时刻，但归因/标题/链接是当前值；该工具不是完整历史快照回放。CSV可导入多维表格，含内部引用应留在授权空间；远程用户不能访问本地路径时填“本地记录不可远程访问”，或提供经授权可访问的PR/仓库链接，不把本地主机路径伪装成在线文档。

当前接入目标见[漏斗绑定](../../../../docs/workflow/bug-funnel.example.json)。URL中的wiki token不是Base app_token；须用正式wiki解析取得obj_type/obj_token，再读取全部table/view/field元数据，按稳定field_id映射，校验类型和只读字段。用户给的view_id只确认所选视图，不能推断已有第二个Tab。

接入步骤：核验用户指定的公司身份→解析Wiki节点→读真实Base/字段/视图/分页记录→写下字段映射与差异→按用户要求配置两个Tab且保留已有数据→按项目+Bug ID幂等更新工程投影→逐条回读核对→从同一明细生成统计。不要将数据表和仪表盘权限/能力混同；实际API不支持所需统计配置时交付CSV和明确的人工配置项，不称已完成在线统计。

表格已有人工维护字段只读保留，不覆盖；来源产品验收禁止本地自动推断。写入超时先查原记录与事件版本，成功一路不因另一失败重发。缺身份/ACL/字段映射只阻塞飞书同步，本地记录与处理继续。长期维护由每次Bug阶段变化执行同步；未配置调度就没有后台自动更新，不私建无限轮询或同步平台。

### 已绑定后的阶段同步

读取绑定中的detail_mapping/statistics_mapping，以field_id写入，不靠字段中文名猜测。使用宿主现有CLI/连接器；本地导出工具不会自动发网络请求。

1. 核验当前身份与目标Base、最新字段类型；分页读取明细，按项目+Bug ID找唯一记录，保留空白模板行。多条同键或人工修改与本地事实冲突时停止该条覆盖并说明。
2. 将details的对应列映射到工程字段；只更新当前Bug，不覆盖产品决定。文本写字符串，数值写number，验证布尔写checkbox；时间字段当前为带时区ISO文本。调查记录需用授权仓库/PR链接，不能把本地路径当在线链接。归因保留hypothesis/confirmed及证据，不只传分类名称。
3. 没有同键时才创建，存在则按record_id更新；超时先重读查证，不盲目再次创建。通过record-get回读此次写入字段及值。
4. 完成本轮范围对账后才从同一批本地JSON生成summary；按metric稳定代码找到统计记录，写数量、分母、比率（0—1小数）、截至时间、时区、明确的项目/批次范围与数据状态。未确认全量时保留数值空白并标“范围未对齐”，不能以当前可读取子集覆盖全量统计；同步中断标记“更新未完成”。
5. 回读所有统计项；原产品Bug清单的PR回写和漏斗工程投影是两个动作，分别验证。统计是最新一次同步快照，不是实时公式；没有Agent执行就不会自动刷新，当天计数须看统计截至日期。后续若存在多个独立批次，先对齐声明的统计范围再整批重算，不用本次局部数据覆盖已有总体。
