# 测试环境验证与用户验收

## 开始

读任务记录、e2e/cases规则、切片结果与实际实现提交。主动检查已有case，只向用户索取缺少的输入、业务目标或授权。由Agent在执行前依据已批准PRD、原文件和领域规则制定独立预期、允许差异与失败条件，写入原case/测试计划；不要求用户逐项设计测试或先审每条研发断言。无法由来源确定的产品选择仍需澄清，研发预期不冒充产品批准。

## 步骤

1. 对照 [测试计划](../../../docs/workflow/templates/test-plan.md) 检查证据：哪些单测/契约/集成/mock浏览器已执行，哪些仍缺；相关检查已通过且无新变化时复用证据。
2. 检查公共组件影响与原型临时代码；涉及界面时执行 [verify-ui](../verify-ui/SKILL.md)，对固定设计与本轮正式页面做同场景截图、差异修复及测试部署复验。纯后端/文档且无可见影响时写明不适用依据。UI、产品行为和后端职责分别检查，不能只看测试数量。
3. 在已授权测试环境和真实依赖下执行case，与独立预期逐项比较；失败时自行复现、定位、修复、定向回归和测试部署复验，按下述预算连续执行，不把每个失败交给用户处理。先查已有任务及副作用，只重测受影响项，能恢复的继续原任务；不得盲重跑已完成模型、改写历史或在staging边开发边修复。完成条件：本轮选定PRD断言及相关回归实际通过，范围外和未执行项单列；不以“用户尚未验收”掩盖研发未测。
4. 用 [交付记录](../../../docs/workflow/templates/delivery.md) 分别报告功能验证、UI对齐和产品验收，附环境、替身、固定版本、成对截图与差异复验记录。界面偏差、缺图或未验证项仍在时不能仅凭功能通过宣布本轮全部通过；需要用户决定的差异具体说明，不能将研发自检留给用户。
5. 测试环境验证通过后调用notify-project向用户的绑定飞书私聊发验收入口、版本、case、验证结果和限制，明确尚未发布staging；默认群可同步摘要。未绑定私聊时报告未发送，不能以群通知代替。需要的通知不再等到上线后才发。
6. 更新当前模块正式文档、长期测试与case引用，核对README的用途、关键链接与使用方法仍正确；按 [文件生命周期](../../../docs/workflow/file-lifecycle.md) 记录已完成范围和历史状态。未完成事项不能因整理文件而消失。
7. 等待用户本人或明确授权决定人确认本轮测试版本。将确认来源、版本、范围和时间写回task/delivery；有问题回到测试环境修复。自动测试通过、沉默、已读或普通群成员意见不代替确认。确认前不调用release-staging。

## 自主测试与修复预算

- 任务记录在首次case准备时固定开始时间、预算和当前轮次；默认最多10轮或2小时，以先到者为准，用户本轮明确约定优先。一个闭环轮次是“执行/复现→对照独立预期→必要修复→复验”，轮询和单条断言不单独计轮。切分任务、换分支/会话或换执行者不重置累计时间和轮次。
- 预算内处理已授权范围的常规缺陷，不因失败、补丁、换Skill或阶段反复请求确认。连续同因失败应更换有证据的诊断/修复方案，不能原样重试。真正缺输入/访问权限/用户决定或出现数据损失、越权风险时，只暂停依赖动作并具体说明，不靠耗尽预算冒充进展。
- 达到任一上限仍有未通过项，停止新增修复/模型提交，保存实际进度和已有任务身份。回报case清单、预期/实际、每轮原因与改动、已验证范围、剩余问题及需要用户决定的具体事项；在任务授权覆盖且已有核验绑定时用notify-project发一次飞书本人通知。通道缺失或回执未知时如实报告，不猜接收人、不自动OAuth或换号，不因通知失败重跑测试。
- 全部本轮case通过时，整理“输入及模拟范围→操作→PRD/原文依据→独立预期→实际结果→证据链接→轮次/耗时”，交用户最终复核并按第5步通知。研发自检和用户业务/视觉验收分别记录；只有用户明确确认本轮版本才可发布staging。
- 该预算依赖当前执行会话和原任务记录，不把SKILL.md当定时服务；中断后按原累计记录恢复，不承诺未经配置的后台定时通知。

## 失败处理

保留失败事实，定位影响和下一步。环境不可用、真实模型超时或阅读器缺失，不使独立单测失效，但对应的真实验收仍未通过。禁止以放宽断言、更新快照、重试吞错或合成结果伪造通过。

## 完成

确认齐备后返回project-workflow进入release-staging；否则记录waiting和可继续项。本Skill不部署staging。确认后若实现/制品变化，重新核对并验收受影响部分；同一确认不重复问。只请求代码/PR的任务按其范围交付，不强制发布。
