# 需求与产品设计交接

## 输入定位

读取根、designend、mockend、cases规则和已有PRD/页面/测试。先检查任务是创建设计还是接收已完成设计；已有信息直接引用。核对designend底稿对应的上线版本。

## 步骤

1. 写出目标、受影响用户动作、本轮范围、成功标准和依据；将推断标为假设。完成条件：本次变化与已有功能可分清。
2. 一开始索取缺少的真实case与预期，使用 [case模板](../../../docs/workflow/templates/case.md)。已有授权输入不重复索要；缺失只限制依赖该输入的工作。完成条件：已提供项可定位，未提供项与影响可见。
3. 逐步推演代表性主路径，再检查本轮关键空/错/恢复场景；每个操作有输入、去向、显示和保存结果。读取 [PRD模板](../../../docs/workflow/templates/prd.md)。完成条件：没有影响实现的隐藏产品决定。
4. 需要建设设计时，在独立designend和mockend中实现；沿用底稿视觉约定，模拟API支持实际点击，界面明确可操作。只接收设计时先运行并操作，不能仅阅读文件名或截图。完成条件：所述场景可演示，mock请求不进入业务后端。
5. 对照界面、PRD、case和mock，列出冲突与全局影响；需要决定时执行 [clarify-task](../clarify-task/SKILL.md)，加载宿主grill-me分析并等待答案，其他独立设计继续。不能自动认定界面或PRD优先。
6. 按 [交接模板](../../../docs/workflow/templates/design-handoff.md) 固定交接提交和剩余问题。完成条件：研发可复现设计，并知道什么可以实现、什么仍是提案。

## 边界

不替产品批准假设；不把原型实现质量当成正式架构要求；不在本阶段顺便改正式frontend或连接真实后端。对现有需求资料足够的任务，不强迫用户重新口述全部设计。
